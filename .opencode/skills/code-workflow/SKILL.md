# 代码工作流（Code Workflow Skill）

> 这是涉及 **任何代码改动** 时的默认 SOP。主代理在识别到代码相关任务时应**显式声明**："本任务遵循 code-workflow 技能"。

---

## 1. 触发场景

只要任务包含以下任一关键词或意图，必须加载本技能：

- 修改 / 新增 / 删除 / 重构 代码
- 审查 / 复核 / Code Review
- 测试 / 验证 / 回归 / 验收
- 复现 / 调试 / 修复 bug
- 实现某个 feature / 接入某个接口

---

## 2. 完整流程（七步法）

```
① 理解目标 → ② 定位现状 → ③ 拆解 TODO → ④ 设计最小改动
                                              ↓
⑦ 汇报      ← ⑥ 委派验证（review/test/debug） ← ⑤ 实施并自审
```

### ① 理解目标

- 复述任务一遍（用自己的话），让用户/上下文有机会纠偏
- 列出**验收标准**：什么算"做完了"？
- 如果缺少关键信息（接口签名、副作用范围、性能要求），**先问一句**

### ② 定位现状

- 用 `search_files` / `list_code_definition_names` 找到相关实现
- 读取关键文件（实现 + 测试 + 调用方）
- 看一眼最近 3–5 条 commit，了解最近上下文
- 输出一段"现状速记"：当前如何工作、为何如此设计

### ③ 拆解 TODO

- 超过 1 步必须列 TODO（使用 `task_progress` 参数同步给 IDE）
- 每条 TODO 必须是**可独立勾选**的具体动作，不要写"完善 foo 模块"这种模糊项

示例：
```
- [ ] 在 src/user.ts 增加 findById 的 null fallback
- [ ] 在 src/user.test.ts 增加 cache miss + DB miss 的用例
- [ ] 跑 pnpm test src/user.test.ts
- [ ] 委派 review 子代理复核
```

### ④ 设计最小改动

- 优先**就地修复**，避免新增抽象
- 如有多个方案，先给出推荐方案 + 一句话理由，再列备选
- 在脑中跑一次"如果回滚这个改动，会发生什么" —— 如果回滚很难，说明改动太大了

### ⑤ 实施并自审

实施过程中遵守：

- 一次只动一个 TODO 项
- 改完一项立刻在脑中过 [`review.md` §3 审查清单](../../agents/review.md)
- 发现自己开始"顺手改无关代码"时**立即停下**

### ⑥ 委派验证

| 触发 | 委派对象 |
|------|----------|
| 改完代码 | `test`（拿可执行证据） |
| 改动影响多模块 | `review`（找回归与边界） |
| 测试失败 / 行为异常 | `debug`（根因分析） |
| 需要外部工具数据 | `tools-runner` |

### ⑦ 汇报

按 [`AGENT.md` §7 标准汇报模板](../../../AGENT.md) 输出。
**禁止**只说"已完成"。

---

## 3. 审查清单（自审 / 委派 review 通用）

- [ ] 实现是否真的满足验收标准？
- [ ] 是否引入对外部接口的破坏性变更？
- [ ] 边界条件（null / 空 / 越界 / 并发 / 超时 / 重试）是否覆盖？
- [ ] 异常是否被正确传播、日志是否带上下文？
- [ ] 是否补了对应测试？未覆盖分支是否在汇报里点名？
- [ ] 是否有调试残留（console.log / 注释代码 / 无 owner TODO）？
- [ ] 命名、目录、依赖方向是否与现有约定一致？
- [ ] 是否产生不可见副作用（写文件 / 发请求 / 改全局状态）？

---

## 4. 验证策略速查

| 改动类型 | 优先验证 |
|----------|----------|
| 业务逻辑分支 | 针对性单测（最窄） |
| 数据结构 / 类型 | typecheck + 相关单测 |
| 公开 API | 单测 + 契约/集成测试 |
| 配置 / 构建 | build + 启动健康检查 |
| 样式 / 格式 | lint / formatter |
| 性能改动 | benchmark / 压测脚本（如有） |

> **永远先跑最窄命令**。只有当最窄命令不足以证明改动正确时，才扩大范围。

---

## 5. 反模式

- ❌ 跳过"理解目标"直接开始改
- ❌ 一次实施 3 项 TODO 不间断自审
- ❌ 用"已修复"代替真正的验证证据
- ❌ 把 TODO 留在代码里却不在汇报中标注
- ❌ 因为"看起来不优雅"就重构无关模块
