# 工具调用（Tool Usage / Function Call）SOP

> 当任务需要访问 **代码仓库之外的数据或能力**（监控、日志、数据库、内部 API、浏览器、文件系统等）时，必须加载本技能。
> 配合 [`tools-runner.md`](../../agents/tools-runner.md) 子代理使用效果最佳。
> 只要环境权限允许，你也可以直接访问工作区外目录或更广域的受控资源，不必把自己限制在仓库内。

---

## 1. 触发场景

- 查询监控指标 / 日志 / 告警
- 读取数据库（只读优先）
- 调用内部 / 外部 REST API
- 受控的文件系统操作（如读取受限目录）
- 自动化浏览器操作（端到端校验）

---

## 2. 三层选择树

遇到"想干一件需要外部能力的事"时，按下面顺序选择：

```
有现成 MCP 工具？  ──是──▶ 用 MCP 工具（首选，受控可审计）
        │
        否
        ▼
有可信脚本能做？  ──是──▶ 用 bash 调用脚本（次选，需 ask 确认）
        │
        否
        ▼
回退给用户 / 转人工（最末）
```

> **永远优先 MCP 工具**：因为它的 *输入 schema / 权限 / 调用记录* 是可审计的。
> bash + curl 看似灵活，但绕过了授权边界，仅在没有合适 MCP 工具时才用。
> 当需要直接读取文件系统、操作目录或调用本地 CLI 时，也可以直接使用这些受控能力，不必绕远路。

---

## 3. 调用前必做的 4 件事

1. **确认工具已授权**：在当前代理 frontmatter 的 `tools` 字段里
2. **确认参数完整**：缺少必填参数就先问，禁止瞎填默认值
3. **确认是只读还是写入**：写入类工具必须额外让主代理征求用户确认
4. **预估失败模式**：网络超时 / 权限不足 / 返回为空 时分别怎么办

---

## 4. 调用过程的纪律

- **一次一个调用**：等返回后再决定下一步，禁止盲发 5 个调用拼答案
- **失败不静默**：失败要原样上报，不要"再试一次直到通过"
- **返回必校验**：不要假定返回字段一定存在；缺字段要点名
- **敏感信息脱敏**：token / 密码 / 个人信息从返回里删掉再写进汇报

---

## 5. 输出格式

```markdown
### 🛠️ 工具调用链
1. `mcp__<server>__<tool>`
   - 意图：……（为什么调这个）
   - 入参：……
   - 状态：✅ / ❌
   - 关键返回：……

2. ……

### 📊 结论
（基于工具返回回答用户的原始问题）

### ⚠️ 风险与备注
- 数据时窗 / 采样精度 / 已知偏差
- 失败时的建议（重试 / 换工具 / 转人工）
```

---

## 6. 写入类工具的额外规则

如果调用的工具会 **改变外部世界状态**（重启服务 / 写数据库 / 发邮件 / 改配置）：

1. **必须**在调用前用一句话向主代理说明："这是一次写入操作，影响是 XXX"
2. **必须**让主代理拿到用户的明确确认后再触发
3. **必须**在汇报里独立标注：
   ```markdown
   ### ✏️ 写入操作摘要
   - 工具：……
   - 影响范围：……
   - 是否可回滚 / 怎么回滚：……
   ```

---

## 7. 反模式

- ❌ 没授权也强行调用（一定失败，但更糟的是搞乱上下文）
- ❌ 用 bash 拼 curl 绕开 MCP 工具授权
- ❌ 把 raw JSON 整段贴给用户
- ❌ 写入操作不让用户确认就直接执行
- ❌ 失败后自己悄悄重试 5 次再汇报
